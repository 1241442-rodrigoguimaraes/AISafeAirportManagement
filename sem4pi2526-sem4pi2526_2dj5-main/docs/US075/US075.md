# US075 - Add a pilot

## 1. Context

Air Transport Companies need pilots registered in the system so that flight plans can later be assigned to valid company pilots. A pilot is a system user and belongs to exactly one Air Transport Company. Each pilot must be certified to operate one or more aircraft models.

### 1.1 List of issues

#### Analysis:

1. **What defines a pilot in the system?**
- A pilot is a system user associated with an Air Transport Company and certified to pilot one or more aircraft models.

2. **Who can add a pilot?**
- Only an authenticated Air Transport Company Collaborator can add pilots to their own company.

3. **What aircraft models can be selected?**
- The pilot can be certified for one or more aircraft models already registered in the system.

4. **Can a pilot exist without certifications?**
- No. The user story explicitly states that a pilot is certified to pilot one or more aircraft models.

#### Design:

- Design of the domain class `Pilot` as an Aggregate Root.
- Design of the builder class `PilotBuilder`.
- Design of the repository interface `PilotRepository`, with `JpaPilotRepository` and `InMemoryPilotRepository`.
- Design of the controller `AddPilotController`.
- Design of the UI `AddPilotUI`.
- Design of `AddPilotAction` to expose the use case in the ATCC console app.
- Update of `RepositoryFactory`, `JpaRepositoryFactory` and `InMemoryRepositoryFactory`.
- Update of the ATCC main menu to include the Add Pilot option.

## 2. Requirements

**US075** - As an Air Transport Company Collaborator, I want to add a pilot to my company. A pilot is a system's user. A pilot is certified to pilot one or more aircraft models.

**Acceptance Criteria:**

- A pilot must be registered as a system user.
- A pilot must belong to the same Air Transport Company as the authenticated ATCC.
- A pilot must be certified for at least one aircraft model.
- A pilot cannot be registered without name, email, phone, password, company or certifications.
- A pilot email must be unique among pilots.
- The operation must only be available to authenticated Air Transport Company Collaborators.
- The pilot must be persisted in the system.

**Dependencies/References:**

- US030: Authentication and authorization.
- US055: Aircraft models must exist so the pilot can be certified.
- US060: Air Transport Companies must exist.
- US061: The authenticated ATCC must be associated with an Air Transport Company.
- US076: The created pilot must be visible in the company pilot roster.
- US080: Flight plan creation will later require selecting a pilot from the company roster.

## 3. Analysis

The use case is performed by an authenticated Air Transport Company Collaborator. The system must identify the company of the authenticated collaborator and automatically associate the new pilot with that company.

The user should not be allowed to choose a different company manually, because the requirement states "my company". This avoids registering pilots in another company's roster.

A pilot must also be a system user. Therefore, the controller creates a `SystemUser` with the `PILOT` role and then creates the `Pilot` aggregate linked to that user.

The pilot's aircraft model certifications are represented as an association between `Pilot` and one or more `AircraftModel` instances.

## 4. Design

The design follows the existing layered architecture:

- **Presentation Layer**: `AddPilotUI` collects the pilot data and the list of certified aircraft models.
- **Application Layer**: `AddPilotController` coordinates the use case, enforces authorization, creates the system user and persists the pilot.
- **Domain Layer**: `Pilot` represents the pilot roster entry and enforces mandatory data and certification rules.
- **Persistence Layer**: `PilotRepository` abstracts pilot persistence, with JPA and in-memory implementations.

### 4.2 Acceptance Tests

**Unit Test 1: Create valid pilot**
- **Action:** Create a pilot with name, email, phone, system user, company and one certified aircraft model.
- **Expected Result:** Pilot is created successfully.

**Unit Test 2: Create pilot without certifications**
- **Action:** Attempt to create a pilot without aircraft model certifications.
- **Expected Result:** The system rejects the operation.

**Unit Test 3: Add pilot as ATCC**
- **Action:** Authenticated ATCC adds a pilot.
- **Expected Result:** Pilot is saved and associated with the ATCC's company.

**Unit Test 4: Duplicate pilot email**
- **Action:** Attempt to add a pilot with an email already used by another pilot.
- **Expected Result:** The system rejects the operation.

**Manual Test 1: Add pilot through ATCC app**
- **Action:** Log in as an ATCC, open Add Pilot, enter valid pilot data and select one or more aircraft models.
- **Expected Result:** Success message is displayed and the pilot is persisted.

## 5. Implementation

### Key Classes

1. `Pilot`: aggregate root representing a pilot in a company's roster.
2. `PilotBuilder`: builder responsible for creating `Pilot` instances.
3. `PilotRepository`: repository abstraction for pilots.
4. `JpaPilotRepository`: JPA persistence implementation.
5. `InMemoryPilotRepository`: in-memory persistence implementation.
6. `AddPilotController`: application controller for US075.
7. `AddPilotUI`: console UI for adding pilots.
8. `AddPilotAction`: menu action to launch the UI.

## 6. Integration/Demonstration

To demonstrate the functionality:

1. Build the project with `mvn test`.
2. Run the bootstrap process if needed.
3. Run the ATCC console application.
4. Log in with an Air Transport Company Collaborator.
5. Select Add Pilot.
6. Insert the pilot's name, email, phone and temporary password.
7. Select one or more aircraft models.
8. Confirm that the pilot is created successfully.

## 7. Observations

The pilot is planned as an Aggregate Root because it has its own lifecycle, repository and direct use cases. The pilot active status should be derived from the associated `SystemUser`, following the same style used for collaborators.
