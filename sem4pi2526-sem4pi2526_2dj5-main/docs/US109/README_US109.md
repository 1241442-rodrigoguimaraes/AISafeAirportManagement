# US109 - Generate and Store Final Simulation Report

## 1. Requirements Engineering

### 1.1 User Story Description

> As a Flight Control Operator, I want a comprehensive report that details the simulation outcomes, including flight execution statuses, safety violation events with timestamps, positions and velocity vectors, and overall validation results, so that I can assess the safety and performance of the flights post-simulation.

### 1.2 Acceptance Criteria

- **AC1:** The report generation thread aggregates data once the simulation concludes.
- **AC2:** The report includes the total number of flights, individual execution statuses, and detailed safety violation events.
- **AC3:** The final validation result, pass or fail, is clearly indicated.
- **AC4:** The complete report is saved to a file for future reference.

## 2. Analysis

The previous SCOMP user stories already keep the main data required for the report:

- **US100/US101:** the controller receives and stores aircraft position updates.
- **US102:** the controller detects safety violations and notifies aircraft with `SIGUSR1`.
- **US103:** updates are synchronized by time step, so safety checks compare positions from the same simulation instant.

The simulation input is read from the project flight-plan DSL files in `SCOMP/flight_plans/*.fp`.

US109 adds persistence of the final simulation outcome. The report is generated only after all child flight processes have ended and have been collected with `waitpid`.

## 3. Design

### 3.1 Report Data

The implementation adds report-specific structures:

- `FlightExecutionStatus`: stores the final status of each flight (`COMPLETED`, `TERMINATED_SAFETY`, `ERROR`, or `RUNNING`).
- `SafetyViolationEvent`: stores each violation's time step, involved flights, positions, velocity vectors, horizontal distance and vertical distance.
- `SimulationReportData`: groups all data passed to the report generation thread.

Velocity vectors are calculated from the last two stored positions of each flight. Since the current simulation model works with discrete time steps, the vector is represented as coordinate variation per second.

### 3.2 Report Generation Thread

After the simulation loop finishes, the parent process:

1. Calls `waitpid` for every child flight process.
2. Builds a `SimulationReportData` instance.
3. Creates a `pthread` for report generation.
4. Waits for the report thread with `pthread_join`.
5. Frees the simulation memory only after the report has been written.

This keeps the report generation separate from the simulation loop and satisfies the requirement for a dedicated report thread.

## 4. Implementation

### 4.1 Flight Statuses

Each flight starts as `FLIGHT_STATUS_RUNNING`.

The final status is updated when the controller deactivates the flight:

- `FLIGHT_STATUS_COMPLETED`: the flight sent its final planned position.
- `FLIGHT_STATUS_TERMINATED_SAFETY`: the flight was stopped due to a safety violation.
- `FLIGHT_STATUS_ERROR`: pipe communication failed or the child ended unexpectedly.

### 4.2 Safety Violation Events

When the controller detects a violation, it now records a `SafetyViolationEvent` before notifying the aircraft.

Each event includes:

- time step;
- violation type;
- involved flight identifiers;
- positions of both aircraft;
- velocity vector of both aircraft;
- horizontal and vertical separation distances.

### 4.3 Report File

The report is saved in:

```text
SCOMP/reports/simulation_report.txt
```

The file contains:

- generation timestamp;
- total number of flights;
- total number of safety violations;
- final validation result (`PASS` only when all flights complete and no violations occur, `FAIL` otherwise);
- individual flight statuses;
- detailed safety violation events.

## 5. Integration / Demonstration

To compile and run the simulation:

```bash
cd SCOMP
chmod +x run-simulation.sh
./run-simulation.sh
```

The script compiles with `-pthread` because the report is generated by a POSIX thread.

After execution, inspect:

```bash
cat reports/simulation_report.txt
```
