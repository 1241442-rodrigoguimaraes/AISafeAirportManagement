# US107 – Notificar a Thread de Geração de Relatório via Variáveis de Condição

## 1. Requirements Engineering

### 1.1 User Story Description

> As a **PO**, I want the simulation system safety violation detection thread to notify the report generation thread through condition variables when a safety violation occurs, so that the report is updated in real-time with accurate information.

---

### 1.2 Acceptance Criteria

- **AC1:** The safety violation detection thread monitors the shared memory for flight conflicts.
- **AC2:** Upon detecting a safety violation, the thread signals the report generation thread using condition variables.
- **AC3:** The report generation thread, waiting on the condition variable, immediately processes the safety violation event and logs it.
- **AC4:** Proper mutex locking is used to ensure thread-safe notification.

---

### 1.3 Found Out Dependencies

| Dependency | Description |
|---|---|
| **SCOMP Shared Memory Infrastructure** | The shared memory (`SharedSimulationArea`) and semaphore (`sem_mem`) must already be initialized to allow the monitor thread to read flight positions. |
| **POSIX Thread Primitives** | `pthread_mutex_t`, `pthread_cond_t`, `pthread_create`, `pthread_cond_wait`, `pthread_cond_signal` — all available via `-lpthread`. |
| **Flight Runner (US107 implicit)** | The child processes (`flight_runner.c`) must be writing positions to shared memory so the monitor can detect conflicts. |

---

### 1.4 Input and Data Flow

**Input (generated by the system):**
- Flight positions read from shared memory (`SharedSimulationArea.flights[i].last_pos`)
- Step counter from `SimulationContext.global_step`

**Output:**
- Violation events logged to stdout in real-time (already implemented via `printf`)
- Violation events written to `./reports/simulation_report.txt` in real-time (new, to be implemented)
- Final consolidated report at simulation shutdown

---

### 1.5 Relevant Diagrams

> No SSD is applicable — this is an internal system communication mechanism between two threads, not a user-facing feature.

---

### 1.6 Other Relevant Remarks

- The mechanism is entirely internal to the parent process: the safety monitor and the report writer are both threads in the parent.
- No new external interfaces or interactions with child processes are required.
- The condition variable avoids busy-waiting in the report thread.

## 3. Design

### 3.1 Rationale

| Interaction ID | Question | Answer | Justification |
|---|---|---|---|
| 1 | Who detects the violation? | `monitor_flights_worker` in `safety_monitor.c` | Iterates flight pairs, computes Haversine + vertical distance, compares to thresholds. |
| 2 | How does the monitor communicate the event? | `pthread_cond_signal(&ctx->cond_violation)` while holding `ctx->mutex` | Standard POSIX condition variable pattern: signal under mutex, waiter re-acquires mutex on wake. |
| 3 | How does the report thread wait? | `pthread_cond_wait(&ctx->cond_violation, &ctx->mutex)` in `report_generation_worker` | Blocks until a violation is signaled; no busy-waiting. |
| 4 | What protects the violation events array? | `ctx->mutex` | Both threads access the array under the same mutex; the monitor writes, the report thread reads. |
| 5 | What protects shared memory reads? | `sem_mem` (named semaphore) | Separate concern: shared memory is accessed by child processes (POSIX) and the monitor thread; protected by a process-shared semaphore. |
| 6 | When is the report file written? | Incrementally, each time a violation is received; plus final summary at shutdown | Ensures real-time logging (AC3) and prevents data loss on crash. |

### 3.2 Sequence Diagram

```
Monitor Thread                          Report Thread
     │                                      │
     │  (detects violation)                  │
     │                                      │
     │  sem_wait(sem_mem)                    │
     │  read flights[i/j].last_pos           │
     │  read flights[i/j].violation_counter  │
     │  sem_post(sem_mem)                    │
     │                                      │
     │  pthread_mutex_lock(&ctx->mutex)      │
     │  record_violation_event(...)          │
     │  pthread_cond_signal(&cond_violation) │
     │  pthread_mutex_unlock(&ctx->mutex)    │
     │                                      │
     │                                      │  (wakes from pthread_cond_wait)
     │                                      │  pthread_mutex_lock(&ctx->mutex)
     │                                      │  process new violation events
     │                                      │  write to report file
     │                                      │  printf to stdout
     │                                      │  pthread_mutex_unlock(&ctx->mutex)
     │                                      │
     │  (continues monitoring)              │  (waits on cond_violation again)
     │                                      │
```

### 3.3 Applied Design Patterns

- **Monitor Object** — The safety monitor thread and report thread coordinate via a shared mutex + condition variable, a classic monitor pattern.
- **Producer-Consumer** — The monitor produces `SafetyViolationEvent` entries; the report thread consumes them.
- **Reader-Writer Lock Separation** — Shared memory (`sem_mem`) and the violation events array (`mutex`) are protected by different synchronization primitives, reflecting different sharing domains (process-shared vs. thread-shared).

## 4. Implementation

### 4.1 Changes to `report_writer.c`

**File:** `SCOMP/report_writer.c`

**What changed:** The `report_generation_worker` function now writes each violation event to `simulation_report.txt` in real-time, rather than only at shutdown.

**Before (lines 10–50):**
```c
void* report_generation_worker(void *arg) {
    SimulationContext *ctx = (SimulationContext*)arg;
    int processed_violation_count = 0;

    while (1) {
        pthread_mutex_lock(&ctx->mutex);

        while (processed_violation_count >= *ctx->stored_violation_count && !ctx->report_shutdown) {
            pthread_cond_wait(&ctx->cond_violation, &ctx->mutex);
        }

        while (processed_violation_count < *ctx->stored_violation_count) {
            SafetyViolationEvent event = ctx->violation_events[processed_violation_count];
            processed_violation_count++;

            printf("[Report] Safety event queued: ...\n");
        }

        if (ctx->report_shutdown) {
            pthread_mutex_unlock(&ctx->mutex);
            break;
        }

        pthread_mutex_unlock(&ctx->mutex);
    }

    SimulationReportData report_data = { ... };
    generate_simulation_report(&report_data);  // only writes at shutdown
    return NULL;
}
```

**After:**
- Open report file at start of worker (`fopen` with `"w"`).
- Write header (timestamp, total flights).
- Inside the inner `while` loop, write each violation event to the file immediately.
- At shutdown, write flight execution statuses and validation result, then close the file.

### 4.2 Changes to `safety_monitor.c`

**File:** `SCOMP/safety_monitor.c`

**What changed:** The `sem_mem` critical section in the violation detection loop is shortened so that the semaphore is released before calling `pthread_cond_signal` and `deactivate_flight`.

**Before (lines 150–190):**
```c
sem_wait(ctx->sem_mem);
// ... read flights, modify violation_counter ...
pthread_mutex_lock(&ctx->mutex);
record_violation_event(...);
pthread_cond_signal(&ctx->cond_violation);
pthread_mutex_unlock(&ctx->mutex);
// ... kill, deactivate_flight ...
sem_post(ctx->sem_mem);  // sem_mem held too long
```

**After:**
```c
sem_wait(ctx->sem_mem);
// copy only what's needed to local variables
Position pos_i = ctx->shared_data->flights[i].last_pos;
Position pos_j = ctx->shared_data->flights[j].last_pos;
int vc_i = ctx->shared_data->flights[i].violation_counter;
int vc_j = ctx->shared_data->flights[j].violation_counter;
// increment counters in shared memory
ctx->shared_data->flights[i].violation_counter++;
ctx->shared_data->flights[j].violation_counter++;
sem_post(ctx->sem_mem);  // release early

pthread_mutex_lock(&ctx->mutex);
record_violation_event(...);   // uses local pos copies
pthread_cond_signal(&ctx->cond_violation);
pthread_mutex_unlock(&ctx->mutex);

// ... kill, deactivate_flight (no sem_mem held) ...
```

## 6. Observations

- The condition variable mechanism was partially present before this US (`pthread_cond_signal` + `pthread_cond_wait` already existed). The main addition is real-time file logging and shortening the `sem_mem` critical section.
- No new types or structures were introduced; the existing `SafetyViolationEvent`, `SimulationContext`, and `SharedSimulationArea` were sufficient.
- The mutex (`ctx->mutex`) serves double duty: protecting the condition variable state and protecting the `violation_events` array. This is acceptable because both uses are in the same threads and the critical sections are short.
- Future improvement: add a `pthread_cond_t` for simulation shutdown instead of polling `ctx->report_shutdown`, to eliminate the remaining busy-wait in the report thread loop.
